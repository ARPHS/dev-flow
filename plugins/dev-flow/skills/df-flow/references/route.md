# 任务分流

## 不进入主流程

以下请求直接完成或直接回答：只改文案、单点重命名、局部格式修复、只读查询、解释代码、只要求审查、只要求设计，以及能够在一次检查中确认的低风险小改动。仍需遵守项目规则，并在声称完成前做适用验证。

## 进入 feature

满足任一条件即可进入 `feature`：跨越多个模块、改变用户可观察行为、涉及权限或错误处理、需要新增或修订测试、存在多个验证步骤、需要在后续会话继续，或用户明确要求持续开发。

先输出开工声明（验收条件、项目命令、基线、验证计划），再边实现边验证。不要为了流程形式创建 PRD 或长计划。

## 进入 project

满足任一条件即可进入 `project`：新项目、架构重组、破坏兼容的公共 API 或数据格式变化、数据迁移、新的认证授权机制或安全边界、跨进程/分布式的并发一致性、有明确指标的性能目标、无法逆转的操作，或多个可行方案会导致不同产品结果。

以下情况仍是 `feature`：向后兼容地新增字段、参数或接口；在已有鉴权体系中给新入口加检查；局部的锁或重试修正；没有明确指标的"顺手优化"。判断不准时选 `feature`，实现中发现影响更大再升级。

先给出问题理解、约束、方案取舍、验收条件、验证方法和风险，然后**停下等待确认**。确认后可以连续推进。

以下情况不再停顿，直接输出开工声明并实现：用户已确认过方案（包括 `df-plan` 已批准的计划）；用户请求中已给出具体方案且没有需要取舍的点；用户明确说"不用确认""直接做"。产品选择、破坏性兼容变化和外部不可逆操作在实施过程中出现时仍需用户决定。

## 示例

| 请求 | 级别 | 理由 |
|---|---|---|
| 修正 README 拼写 | 不进入 | 单点文案 |
| 解释 `export.py` 的分页逻辑 | 不进入 | 只读 |
| 给 CLI 增加 `--json` 输出 | feature | 改变可观察行为、需新增测试 |
| 给订单接口返回值加一个 `currency` 字段 | feature | 向后兼容的新增 |
| 把订单接口的 `amount` 从元改成分 | project | 破坏兼容的数据格式变化 |
| 导出偶尔漏掉最后一页 | feature + `df-debug` | 根因不明的缺陷 |
| 把存储从 JSON 文件换成 SQLite | project | 数据格式变化、需迁移 |
| 从零写一个记账 CLI | project | 新项目、需确定范围和格式 |

## 用户指定级别

用户明确说"按 quick/feature/project 做"或"不要建台账"时遵从用户。只有存在数据丢失、安全或不可逆风险时，才说明风险并建议升级，由用户决定。

## 升级和降级

实现中发现数据、兼容性、性能或安全影响高于预期时升级级别并说明原因；升级到 `project` 时补齐设计并停顿确认。证据表明任务比预期简单时可以降级，不保留无用台账。级别只描述工作量，不改变用户授权边界。
