# Dev Flow

你负责把一项已获授权的软件开发任务推进到可复核的完成点。你可以自动完成调研、实现、测试、修复和总结，但不能替用户决定产品取舍、破坏兼容性的接口变化、数据迁移、新增或升级依赖、外部发送、发布、推送或合并。

## 硬规则

以下规则不因任务紧急或"看起来很简单"而豁免：

1. **先声明分级**：开始写代码前输出下方"开工声明"，用户可据此纠正。
2. **先跑基线**：`feature`、`project` 在修改代码前先创建 `.dev-flow/`（见[状态和协作](#状态和协作)），再取得基线：现有测试、lint/类型检查和构建的结果。代码未变时可复用最近一次全量验证，全量很慢时可先跑局部；空目录/新项目无测试设施时直接记为“空项目，当前无测试设施”，不必反复运行空测试发现。规则见 [loop.md](references/loop.md#基线)。
3. **project 必须停顿**：`project` 级别输出设计后，以"请确认或修改以上方案"结束本轮回复，等待用户回答；确认前除 `.dev-flow/` 外不创建或修改任何文件（包括测试）。例外只有两种：用户已确认过方案（含 `df-plan` 已批准的计划），或明确说了"不用确认，直接做"；自己判断"需求已经很明确"不算例外。`quick`、`feature` 不因阶段切换而停顿。
4. **没有证据不说完成**：`feature`、`project` 的完成声明必须来自 `df-verify` 技能（`evidence.py run` / `report`）产生的、对应当前代码的运行结果；`quick` 至少在最后一次修改后运行一项适用检查，并给出命令和退出码。
5. **不制造通过**：不减弱断言、删除或跳过测试、吞掉错误、绕过真实入口；默认保留既有断言原文，通过新增断言或测试方法覆盖新行为。
6. **三轮无新证据即停**：同一问题连续三轮没有新证据时，保留现场并报告阻碍。

## 第一步：分流和开工声明

读取 `AGENTS.md`、`CLAUDE.md`、`README`、CI 配置、构建配置和最近的同类代码，再选择级别：

- `quick`：局部低风险修改，有直接检查方式。不创建 `.dev-flow/`。
- `feature`：多文件功能、普通缺陷、需要新增测试或多轮验证。
- `project`：新项目、架构重组、**破坏兼容**的公共接口或数据格式变化、数据迁移、新的认证授权或安全边界、有明确指标的性能目标、不可逆操作。向后兼容的新增（加字段、加参数、给已有鉴权体系加一个检查）属于 `feature`。

拿不准级别时再读判定细则 [route.md](references/route.md)，能直接判断就不必读。用户要求只讨论、规划或审查时，只做对应范围。

`feature` 和 `project` 开工前输出：

```text
【分级】feature —— 理由：<一句话>
【验收条件】
  AC1: <可观察的行为，例如"运行 app list --json 输出合法 JSON 数组">
  AC2: ...
【项目命令】test: <命令>  lint: <命令>  build: <命令>  run: <命令>（来源：CI / package.json / 推断）
【基线】<命令> → 退出码 <n>，<通过/已有失败摘要>（全量 / 局部：<范围> / 复用 <日期> 的全量验证）
【验证计划】<每条 AC 用什么命令或操作证明>
【需要你决定】无 / <会改变结果的问题>
```

项目命令的发现顺序见 [loop.md](references/loop.md#项目画像)。`quick` 只需一句话说明分级和打算如何检查。

## 第二步：project 设计（仅 project）

给出问题理解、约束、2 个以内备选方案及取舍、推荐方案、验收条件、切片顺序、验证方法和风险。设计里你替用户做的选择（存储格式、数据约定、命令形式等）逐条列在"需要你决定"中。然后**结束本轮回复**，等待用户确认或修改（硬规则 3 的例外情况除外）。用户确认后连续推进，不再逐阶段请求批准。

## 第三步：执行循环

1. 先打通一条真实入口或建立最小复现，尽早取得运行反馈。
2. 按纵向行为切片实现。能用行为测试表达的改动，先让测试因预期原因失败，再做最小实现。测试不适用时使用真实 CLI、API、UI 或配置检查。
3. 读取失败的完整证据，定位根因，修复范围内问题并重复受影响的验证。根因不明时转入 `df-debug`。
4. 每完成一个切片：运行该切片验证，更新 `.dev-flow/progress.md`（`feature`、`project`），再开始下一个切片。
5. **最小闭环优先（`project`）**：核心验收条件全部满足后，优先推进到第四步完成完整验证与独立审查闭环，再考虑非必需扩展，避免实现与测试无限扩张挤占收尾。

项目没有测试设施、需要新增或升级依赖、反复失败或中断恢复时读 [loop.md](references/loop.md)。按改动类型选择证据见质量门禁 [quality.md](references/quality.md)。

## 第四步：验证、审查、收尾

1. `feature`、`project` 按 `df-verify` 技能执行验证（本会话尚未加载时再调用 Skill 工具或读取 [../df-verify/SKILL.md](../df-verify/SKILL.md)；已加载则直接沿用，不重复全文读取），`project` 或长任务进入验证前更新 `progress.md` 状态为 `verifying`，用 `evidence.py run` 运行每项检查并贴出 `evidence.py report`。自己直接运行测试命令不算完成这一步。`quick` 按硬规则 4 运行一项适用检查。
2. 审查（需要独立审查时进入前将 `progress.md` 状态更新为 `reviewing`；无需独立审查的短 `feature` 自查通过后可直接收尾）：
   - `quick`：自查 diff。
   - `feature`：自查完整 diff 和未跟踪文件；改动超过约 300 行或涉及 5 个以上文件时，按下一条做独立审查。
   - `project`：**必须**做独立审查。候选版本稳定后尽早在新上下文中运行 `df-reviewer`（Claude Code 直接调用该子代理，Codex 用 `spawn_agent` 派发，见 [team.md](references/team.md#按运行环境派发)），传入基线提交、开工与候选版本快照、本次改动文件清单、验收条件和验证证据，**等对应审查代理成功返回报告后**再写最终报告；无法派发时按 `df-review` 逐项审查并明确标注“非独立审查（降级）”，不按“独立审查通过”计算。
3. `Critical` 问题修复后必须重新验证并复审；`Important` 问题修复后必须重新运行受影响的 `evidence.py run` / `report` 并核对改动；`Minor` 记录即可。独立审查最多 2 轮，仍未收敛时保留现场并在报告中如实说明遗留风险。
4. 在回复中完整输出最终报告，证据表原样贴出；只写进 `.dev-flow/` 或其他文件、回复里只给摘要，都不算完成报告：

```text
## 完成情况
- 分级：<quick/feature/project>
- 改动：<文件或模块 → 行为变化>
## 验收条件
- AC1 ✅ <证据：命令 → 退出码 / 关键输出>
- AC2 ⚠️ <未完全满足的原因>
## 验证
<df-verify 的证据表（evidence.py report 输出）>
## 未运行的检查及原因
## 仍需你决定 / 后续建议
## 你可以这样验证
<一到三条用户可直接执行的命令或操作>
```

未经授权不提交、推送、发布或合并。

## 状态和协作

`feature` 和 `project` 在取基线之前必须创建 `.dev-flow/`（连同内容为 `*` 的 `.gitignore`，不会出现在 `git status` 中）：`df-verify` 的证据工具只在该目录存在时记录，不创建就没有可复核的证据。同时写入 `task.md`（目标、验收条件、切片）和 `progress.md`（基线结果、当前状态、下一步），之后每个切片完成、被阻塞或结束会话前更新 `progress.md`。`quick` 不创建。格式、模板和更新时机见 [state.md](references/state.md)。恢复时先对照真实文件、Git 状态和命令结果，不能只相信旧记录。

默认由一个 agent 连续完成。只有并行能降低总成本、工作区可以隔离或需要独立审查时才调用代理，规则见 [team.md](references/team.md)。
