# Review

## 1. 固定审查对象

- 代码：确定基线（用户指定、`.dev-flow/` 记录的开工 HEAD，或 `git merge-base HEAD <主分支>`），查看 `git diff <基线>` 的完整内容和 `git status` 中的未跟踪文件。不能只看最后一个文件或最后一次提交。
- 方案：对照项目现状、成功标准、依赖和更简单的选择。
- 记录审查对应的版本（提交加 `git status --short` 摘要，或 df-verify 证据中的快照 id），结论只对这个版本有效。

## 2. 逐项检查

**需求**
- [ ] 每条验收条件都有对应实现和运行证据
- [ ] 正常路径、边界、错误、权限、兼容性
- [ ] 没有超出范围的行为变化

**工程**
- [ ] 设计清晰，复用现有模式，没有重复逻辑
- [ ] 测试验证行为而非实现文字；没有被删除、跳过或减弱的断言
- [ ] 错误没有被吞掉；没有绕过真实入口的临时代码
- [ ] 安全：输入处理、鉴权、密钥、新增依赖（见 [quality.md](../df-flow/references/quality.md#安全检查)）
- [ ] 可以自行运行的验证已实际运行，结果与声明一致

## 3. 报告

```text
## 审查结论（版本：<提交/快照 id>，基线：<提交>）
结论：可以合入 / 修复后合入 / 需要重新设计
### Critical
- [文件:行] <问题> —— 影响：<…> —— 依据：<复现命令或代码引用> —— 建议：<…>
### Important
### Minor
### 已核对的证据
```

- Critical：数据丢失、安全漏洞、核心验收条件不满足、构建或测试被破坏。
- Important：边界或错误路径缺陷、测试无效、明显的维护风险。
- Minor：命名、风格、可读性。

没有问题时直接说明未发现阻塞项，不凑问题。不把未要求的未来功能评为缺陷。

## 4. 修复和复审

Critical 和 Important 在用户要求的范围内修复并复验。任何实质修改、同步主分支或方案变更后，重新检查受影响范围。未经用户授权，审查不自动合并、推送或发布。
