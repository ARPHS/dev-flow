# 质量门禁

质量门禁按成本从低到高排列。优先让代码结构、API、类型系统、lint、编译器、测试和 CI 机械地拒绝错误模式，再用运行时验证取得行为证据，最后让文字规则和人工审查处理仍需判断的部分。

每次反复出现的纠正都要考虑是否可以固化为更清晰的接口、更严格的数据结构、静态检查、行为测试或运行时断言。规则和评论不能替代可执行约束，也不能为临时绕过提供理由。

## 按改动选择证据

| 改动类型 | 必需证据 |
|---|---|
| 业务逻辑 | 输入输出、边界值、错误路径、权限的测试 |
| CLI | 真实调用的命令、退出码和输出；错误参数的行为 |
| API | 兼容调用、错误响应、契约或集成测试 |
| UI | 真实用户路径。有浏览器自动化（Playwright、浏览器 MCP）时操作并截图；没有时列出需要用户手动验证的步骤，不能声称已验证 |
| 数据/迁移 | 旧数据演练、迁移回滚或一致性检查 |
| 性能 | 相同环境、负载和指标的前后测量 |
| 并发 | 状态不变量、重试、重复调用和故障恢复 |
| 配置/构建 | 实际加载或构建一次 |

## 安全检查

涉及以下内容时逐项确认：

- 输入处理：注入（SQL、命令、路径）、反序列化、未校验的外部输入。
- 认证授权：新入口是否经过鉴权，越权访问是否被拒绝。
- 密钥：diff 中没有硬编码的密钥、令牌或连接串，日志不输出敏感数据。
- 依赖：新增依赖的来源、维护状态和许可证；项目有审计命令（`npm audit`、`pip-audit` 等）时运行。

## 测试有效性

- 新测试在实现前应因预期原因失败；无法做到时说明原因。
- 不修改既有断言让测试通过，除非需求本身改变，并在报告中指出。
- 不用 mock 替换被测行为本身。

## 证据绑定版本

任何验证结果都绑定当前代码。不能把静态阅读、代理报告或旧日志当作新版本的运行证据。`df-verify` 用指纹脚本记录证据对应的版本。
