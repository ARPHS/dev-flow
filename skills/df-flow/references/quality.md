# 质量门禁

质量门禁按成本从低到高排列。优先让代码结构、API、类型系统、lint、编译器、测试和 CI 机械地拒绝错误模式，再用运行时验证取得行为证据，最后让文字规则和人工审查处理仍需判断的部分。

每次反复出现的纠正都要考虑是否可以固化为更清晰的接口、更严格的数据结构、静态检查、行为测试或运行时断言。不要只继续增加规则文本。规则和评论不能替代可执行约束，也不能为临时绕过提供理由。

根据改动选择证据：

- 业务逻辑检查输入、输出、边界、错误路径和权限。
- UI 改动走真实用户路径，记录截图、状态或浏览器结果。
- API 改动检查兼容调用、错误响应和契约测试。
- 数据改动使用旧数据演练、迁移回滚或一致性检查。
- 性能改动使用相同环境、负载和指标做前后测量。
- 并发改动检查状态不变量、重试、重复调用和故障恢复。

任何验证结果都绑定当前代码或提交。不能把静态阅读、代理报告或旧日志当作新版本的运行证据。
