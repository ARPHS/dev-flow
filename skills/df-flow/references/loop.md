# 实现循环

## 进入任务

1. 确认工作目录、当前分支、`git status` 和已有改动。保留用户已有修改，不把无关文件加入任务。
2. 完成项目画像（见下节）。
3. `feature`、`project` 运行基线：测试、lint/类型检查、构建。记录命令、退出码和失败摘要。基线已有失败时记下失败项名称，后续不修复范围外的基线失败，但也不能让它掩盖新失败。
4. 需要隔离时按项目约定创建分支或 worktree；不需要时直接使用当前工作区。

## 项目画像

按以下顺序发现命令，前面的来源优先：

1. 用户指令、`AGENTS.md`、`CLAUDE.md`、`CONTRIBUTING.md` 中写明的命令。
2. CI 配置：`.github/workflows/*.yml`、`.gitlab-ci.yml`、`azure-pipelines.yml` 等。CI 实际运行的命令最可靠。
3. 任务脚本：`package.json` scripts、`Makefile`、`justfile`、`Taskfile.yml`、`pyproject.toml`（含 tox/nox/hatch）、`Cargo.toml`、`go.mod`、`build.gradle`、`pom.xml`、`*.csproj`。
4. 只有前三者都不存在时才推断，并在开工声明中标明"推断"。

`feature`、`project` 把结果写入 `.flow/project.md`，后续会话直接复用；命令失效时更新它。

## 没有测试设施时

- 改动是可独立运行的逻辑（解析、计算、转换）且项目语言有标准测试工具：先搭建最小测试框架，作为一个独立切片，并在报告中说明。
- 搭建成本明显高于改动本身，或用户明确不希望引入：改用真实入口验证（CLI 调用、HTTP 请求、脚本演练），并保存可重放的命令。
- 不允许以"没有测试"为由跳过验证。

## 行为切片

每个切片都应能由用户路径、公共接口、命令、测试或测量观察到。优先选择能验证架构假设的最小路径，再补边界和错误路径。不要先写一批无法单独验证的基础层代码。

行为变化通常采用红、绿、重构：先写能因预期原因失败的测试并确认失败，再写最小实现，通过后整理设计。文档、配置、样式或测试工具等改动采用实际适用的检查，不制造只匹配实现文本的测试。

## 检查点

- 每个切片完成并验证通过后更新 `.flow/progress.md`。
- 被阻塞、准备向用户提问、上下文接近上限或即将结束会话时，也要先更新 `progress.md`。
- 用户授权提交时，在任务分支上按切片提交，提交信息说明行为变化。未授权提交时，在 `progress.md` 记录 `git diff --stat` 作为切片边界，不自行提交或 stash。

## 依赖和范围

- 新增、升级或删除第三方依赖属于决策边界：说明用途、替代方案和许可证，`feature` 及以上需用户同意（用户事先授权的除外）。优先使用项目已有依赖和标准库。
- 发现范围外问题时记录在报告的"后续建议"中，不顺手修改。

## 失败处理

命令失败时保留完整命令、工作目录、退出码和关键输出。先区分代码失败、测试失败、环境失败和基线失败。重复失败时缩小复现范围并改变观测手段。连续三轮无新证据时停止当前分支，记录阻碍和需要的决定，不伪造进展。

## 收尾

检查完整 diff 和未跟踪文件，确认范围、错误处理、兼容性和验收条件。运行最终验证，确认结果对应当前代码而非旧提交。用户明确授权提交、合并或推送时，先重新核对基线和工作区，再执行对应动作。
