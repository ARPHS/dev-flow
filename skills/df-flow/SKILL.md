# Dev Flow

你负责把一项已获授权的软件开发任务推进到可复核的完成点。你可以自动完成调研、实现、测试、修复和总结，但不能替用户决定产品取舍、破坏兼容性的接口变化、数据迁移、新增或升级依赖、外部发送、发布、推送或合并。

## 硬规则

以下规则不因任务紧急或"看起来很简单"而豁免：

1. **先声明分级**：开始写代码前输出下方"开工声明"，用户可据此纠正。
2. **先跑基线**：`feature`、`project` 在修改代码前运行现有测试、lint/类型检查和构建，记录结果作为基线。
3. **project 必须停顿**：`project` 级别输出设计后停下等待用户确认，确认前不写实现代码。`quick`、`feature` 不因阶段切换而停顿。
4. **没有证据不说完成**：完成声明必须来自 `df-verify` 产生的、对应当前代码的运行结果。
5. **不制造通过**：不减弱断言、删除或跳过测试、吞掉错误、绕过真实入口。
6. **三轮无新证据即停**：同一问题连续三轮没有新证据时，保留现场并报告阻碍。

## 第一步：分流和开工声明

读取 `AGENTS.md`、`CLAUDE.md`、`README`、CI 配置、构建配置和最近的同类代码，再选择级别：

- `quick`：局部低风险修改，有直接检查方式。不创建 `.flow/`。
- `feature`：多文件功能、普通缺陷、需要新增测试或多轮验证。
- `project`：新项目、架构变化、公共接口或数据格式、迁移、认证授权、安全、并发、性能目标、不可逆操作。

判定细则见 [route.md](references/route.md)。用户要求只讨论、规划或审查时，只做对应范围。

`feature` 和 `project` 开工前输出：

```text
【分级】feature —— 理由：<一句话>
【验收条件】
  AC1: <可观察的行为，例如"运行 app list --json 输出合法 JSON 数组">
  AC2: ...
【项目命令】test: <命令>  lint: <命令>  build: <命令>  run: <命令>（来源：CI / package.json / 推断）
【基线】<命令> → 退出码 <n>，<通过/已有失败摘要>
【验证计划】<每条 AC 用什么命令或操作证明>
【需要你决定】无 / <会改变结果的问题>
```

项目命令的发现顺序见 [loop.md](references/loop.md#项目画像)。`quick` 只需一句话说明分级和打算如何检查。

## 第二步：project 设计（仅 project）

给出问题理解、约束、2 个以内备选方案及取舍、推荐方案、验收条件、切片顺序、验证方法和风险。然后**停下**，等待用户确认或修改。用户确认后连续推进，不再逐阶段请求批准。

## 第三步：执行循环

1. 先打通一条真实入口或建立最小复现，尽早取得运行反馈。
2. 按纵向行为切片实现。能用行为测试表达的改动，先让测试因预期原因失败，再做最小实现。测试不适用时使用真实 CLI、API、UI 或配置检查。
3. 读取失败的完整证据，定位根因，修复范围内问题并重复受影响的验证。根因不明时转入 `df-debug`。
4. 每完成一个切片：运行该切片验证，更新 `.flow/progress.md`（若存在），再开始下一个切片。

详细循环、检查点和依赖策略见 [loop.md](references/loop.md)，质量门禁见 [quality.md](references/quality.md)。

## 第四步：验证、审查、收尾

1. 调用 `df-verify` 完成最终验证。证据必须对应当前代码。
2. 审查：
   - `quick`：自查 diff。
   - `feature`：自查完整 diff 和未跟踪文件；改动超过约 300 行或涉及 5 个以上文件时，按下一条做独立审查。
   - `project`：**必须**做独立审查。有 `df-reviewer` 子代理时在新上下文中调用它，传入基线提交、验收条件和验证证据；没有子代理能力时，按 `df-review` 的步骤逐项审查并在报告中注明"非独立审查"。
3. Critical、Important 问题修复后重新验证，Minor 记录即可。
4. 输出最终报告：

```text
## 完成情况
- 分级：<quick/feature/project>
- 改动：<文件或模块 → 行为变化>
## 验收条件
- AC1 ✅ <证据：命令 → 退出码 / 关键输出>
- AC2 ⚠️ <未完全满足的原因>
## 验证
| 命令 | 目录 | 退出码 | 结果 |
## 未运行的检查及原因
## 仍需你决定 / 后续建议
## 你可以这样验证
<一到三条用户可直接执行的命令或操作>
```

未经授权不提交、推送、发布或合并。

## 状态和协作

只有 `feature`、`project`、需要跨会话恢复或用户要求时才创建 `.flow/`。格式、模板和更新时机见 [state.md](references/state.md)。恢复时先对照真实文件、Git 状态和命令结果，不能只相信旧记录。

默认由一个 agent 连续完成。只有并行能降低总成本、工作区可以隔离或需要独立审查时才调用代理，规则见 [team.md](references/team.md)。
