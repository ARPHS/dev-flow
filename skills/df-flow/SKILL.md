# Dev Flow

你负责把一项已获授权的软件开发任务推进到可复核的完成点。你可以自动完成调研、实现、测试、修复和总结，但不能替用户决定产品取舍、破坏兼容性的接口变化、数据迁移、外部发送、发布、推送或合并。

## 先分流

先读取项目的 `AGENTS.md`、`CLAUDE.md`、`README`、构建配置和最近的同类代码。根据失败成本、数据影响、兼容性、验证难度和任务跨度选择工作量：

- `quick` 适用于局部低风险修改，有直接的检查方式，不创建 `.flow/`。
- `feature` 适用于多文件功能、普通缺陷或需要多轮验证的修改，记录验收条件和进度。
- `project` 适用于新项目、架构变化、公共接口、数据迁移、安全或性能任务，先形成可执行设计再实施。

用户明确要求讨论、规划或审查时，只做对应范围。用户明确要求实现时，除真实决策边界外持续推进，不在每个阶段重复请求确认。

详细路由见 [route.md](references/route.md)。

## 执行循环

1. 把用户目标转成少量可观察的验收条件，指出仍会改变结果的决策。
2. 先打通一条真实入口或建立最小复现，尽早取得运行反馈。
3. 按纵向行为切片实现。能用行为测试表达的改动，先让测试因预期原因失败，再做最小实现。测试不适用时使用真实 CLI、API、UI 或配置检查。
4. 读取失败的完整证据，定位根因，修复范围内问题并重复受影响的验证。不要通过减弱断言、删除测试或绕过真实入口制造通过结果。
5. 完成前调用 `df-verify`，按改动运行适用的测试、类型检查、lint、构建、真实入口和性能测量。完成声明必须引用实际证据。
6. 对完成结果做需求和工程两方面审查。Critical、Important 问题解决后再收尾，Minor 问题记录即可。

详细循环见 [loop.md](references/loop.md)，质量门禁见 [quality.md](references/quality.md)。

## 状态、协作和终点

只有需要跨会话恢复、多人交接、复杂变更或长时间执行时才创建目标项目的 `.flow/`。保存目标、验收条件、当前任务、实际验证、待决事项和下一步，不复制完整对话。恢复时先对照真实文件、Git 状态和命令结果，不能只相信旧文字记录。状态格式见 [state.md](references/state.md)。

默认由一个 agent 连续完成。只有并行能降低总成本、工作区可以隔离或需要独立审查时才调用代理。协作规则见 [team.md](references/team.md)。

最终报告说明改了什么、用户怎样验证、运行了哪些命令及结果、哪些事项仍需用户决定。未经授权不提交、推送、发布或合并。
